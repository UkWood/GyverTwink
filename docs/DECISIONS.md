# Журнал решений

Формат: дата — решение — причина. Новые записи добавляются сверху.

## 2026-10-22
- **Этап 3 закрыт, версия прошивки 1.4** (новые эффекты, расписание, токен; MQTT/Home Assistant отменены). Дальше - этап 4 (приложение) и проверка на плате по `docs/HARDWARE_CHECKLIST.md`.
- **Токен для управления (этап 3, `guard.ino`).** Необязательный; без токена всё как раньше.
  - **Токен меняют и снимают только при открытом окне обслуживания** (три нажатия кнопки, то же окно, что для OTA), старый токен не нужен. Причина: если задать токен мог бы любой в сети, он мог бы отобрать управление и заблокировать владельца; а забытый токен иначе потребовал бы сброса прошивки. Ценой остаётся короткое окно (5 минут), пока токен может задать любой в сети; окно закрывается после смены.
  - **Проверка на всех API веба, и GET тоже** (состояние, сцены, координаты раскрывают много); открыты только страница и `GET /api/auth`. Запись в `/update` токен не требует (защищена физическим окном).
  - **Подбор:** 5 неверных токенов с одного адреса - блокировка на 60 с, таблица на 4 адреса (блокировки вытесняются в последнюю очередь). Блокировка по адресу, а не глобальная: иначе любой мог бы заблокировать владельца. Запрос без токена подбором не считается, а страница не шлёт запросы с устаревшим токеном (после первого отказа - вход).
  - **UDP-протокол токена не знает**: менять протокол можно только вместе с приложением (этап 4), а приложение его ввести не умеет. По умолчанию UDP открыт (приложение продолжает работать); владелец может закрыть команды записи `{2,..}`, `{3,..}`, `{4,..}` (флаг `udpLock`, ACK-статус 3 `PKT_DENIED`), запросы `{0}`, `{1}`, `{5}`, `{7}` остаются. Это честная плата: токен на вебе без закрытого UDP защищает только веб.
  - Токен хранится в EEPROM открытым текстом и ходит по HTTP без шифрования (HTTPS на ESP8266 слишком дорог по ОЗУ): защита от случайных гостей, а не от прослушивания. Блок `Guard` - в конце EEPROM. Имена без `auth`/`access` (конфликты с SDK и POSIX).
- **Расписание (этап 3, `schedule.ino`).** Включение и выключение гирлянды по времени суток или относительно рассвета/заката, по дням недели.
  - **Источник времени:** NTP (`configTime`), только если при старте гирлянда подключена к роутеру; в режиме точки доступа интернета нет, поэтому время может прислать страница (`POST /api/time`, телефон знает время). RTC нет: после перезагрузки время пропадает, страница передаёт его снова при открытии, если расписание включено.
  - **События, а не состояние:** событие срабатывает один раз в свою минуту; ручное включение/выключение действует до следующего. Причина: иначе расписание «воевало» бы с владельцем. После скачка времени (NTP, ручная установка) пропущенные события не повторяются; короткая задержка цикла (до 5 минут) событий не теряет. При совпадении включения и выключения побеждает включение.
  - **Часовой пояс - постоянный сдвиг в минутах**, без правил летнего времени (проще и без строки POSIX TZ; цена - ручная смена пояса дважды в год). Возможное улучшение позже.
  - **Рассвет и закат** считаются по формулам NOAA на `float` раз в минуту и по запросу страницы (точность около минуты, проверено на пяти городах включая южное полушарие, полярный день и ночь дают «нет события»). Координаты вводятся вручную: геолокация в браузере требует HTTPS, которого на ESP нет.
  - Настройки - новый блок EEPROM `Sched` в конце (после `effsX`). Протокол UDP и приложение не затронуты; события пропускаются во время калибровки и записи прошивки.
- **Новые эффекты (этап 3): номера 22–27, `EFFECT_COUNT` = 28.** Звёзды, бегущие огни, огонь, дыхание, волны по высоте, волны от центра (`effects.ino`).
  - Настройки (избранное, масштаб, скорость) лежат в **новом блоке EEPROM `effsX[6]` в конце** (после `pwr`), блок `effs[22]` не менялся: иначе сдвинулись бы адреса и сбросилась калибровка.
    Доступ только через `effAt(n)`. Значения по умолчанию - `fxDefaults()`; **в избранное по умолчанию не входят**, чтобы автосмена у существующих установок не начала показывать новые эффекты без ведома владельца.
  - Протокол только расширен: `{4,0,n}` принимает n до 27 (старое приложение шлёт только 0–21, ответов `curEff` оно не получает). В приложение новые эффекты не добавлены (этап 4).
  - **Сцены: формат файла v2** (запись + `fx[6]`). Файл v1 (прошивка 1.3) читается и переводится в v2 при следующей записи; настройки новых эффектов в старой сцене - по умолчанию. Запись v1 читается по одной (стек мал).
  - Вся арифметика целочисленная (float на ESP8266 медленный, кадр считается на сотни светодиодов); «звёзды» хранят кадр в самом `leds[]`, отдельный буфер не нужен.
  - Предположение: ось Y направлена вниз, как в кадре камеры (огонь поднимается к меньшему Y). Внешний вид на настоящей ленте не проверялся - за владельцем (`docs/HARDWARE_CHECKLIST.md`).
- **MQTT / Home Assistant исключены из этапа 3 (отменено владельцем).** Остаются: новые эффекты, расписание по NTP, простая аутентификация (токен).
  Побочный эффект: отпадает самая затратная по ОЗУ часть этапа (клиент MQTT, буферы, переподключение); запаса флеш (по CI ~509 КБ до лимита OTA) и ОЗУ достаточно.

## 2026-10-20
- **Этап 2 закрыт (веб-интерфейс).** Итог: управление, эффекты, сцены, калибровка по видео, редактор координат, OTA, mDNS; версия прошивки 1.3. Вся логика проверена на ПК, страница - в настоящем Chromium
  (включая настоящее видео VP8 и настоящий multipart-запрос). Не проверено на плате: сеть/mDNS, LittleFS и OTA во флеше, кнопка, лента, камера телефона - `docs/HARDWARE_CHECKLIST.md`.
  Известные риски: ESP8266WebServer однопоточный (запросы обслуживаются по очереди, показ ленты на время `show` блокирует прерывания), `char`-буферы ответов подобраны под малый стек ESP8266,
  разбор видео зависит от кодека, который понимает браузер телефона.
- **ACK как необязательное расширение протокола**: флаг 0x80 в байте команды + байт seq; ответ `{6, cmd, seq, status}`; запрос `{5}` возвращает версию расширения.
  Причина: протокол только расширяется. Старое приложение отправляет каждый пакет дважды с паузой 15 мс, а прошивка отсеивала повтор 50-мс «антидребезгом» -
  для клиентов с ACK повторы отсеиваются по seq, для старых поведение прежнее. Дубликаты не выполняются повторно (важно для «следующий эффект»).

- **ACK в приложении (v1.8)**: после ответа на `{5}` команды уходят по одной с seq, следующая - после ACK; повтор через 200 мс, до 5 попыток;
  ожидающие значения ползунков сливаются. Запросы `{0}` (широковещательный поиск) и `{5}` всегда без ACK. Команды строго по очереди, потому что прошивка
  помнит только последний seq - повтор более старой команды выполнился бы заново. Логика проверена Java-моделью прошивки с потерями пакетов 40%
  (каждая команда выполняется не более одного раза); сборка Processing/Android здесь недоступна, APK не пересобирался.

- **Ограничение тока считается в прошивке самостоятельно** (`power.ino`), а не через `FastLED.setMaxPowerInMilliAmps()`: кадры выводятся
  через `strip->showLeds()`, в обход `FastLED.show()`, где стоит лимит. Используется `calculate_max_brightness_for_power_vmA`; лимит ×0.7,
  потому что FastLED считает 42 мА на белый светодиод, а реально до 60 мА. Лимит по умолчанию выключен (`POWER_LIMIT_MA 0`), чтобы не менять яркость у существующих установок.
- **Настройка лимита лежит в отдельном блоке EEPROM в конце** (после `xy`), чтобы не сдвигать блоки и не терять калибровку после обновления.
  Для этого в вендорной `EEManager` адрес в `begin()` расширен с `uint8_t` до `uint16_t` (иначе адрес 1151 обрезался бы).

- **Пароль точки доступа задаётся в портале настройки**: форма «Access Point» теперь требует пароль (8-31 символ). В режиме AP SSID в `portalCfg` очищается, а поле `pass`
  хранит пароль точки - так не меняется размер `PortalCfg` (первый блок EEPROM, его рост сдвинул бы все остальные). `GT_AP_PASS` остаётся запасным для старых установок
  (`SSID` непустой или `pass` короче 8) и для отката после неудачного подключения к роутеру (там в `pass` лежит пароль роутера - его для точки не используем).
  Сам портал настройки («ESP Config») по-прежнему открытая сеть: он нужен только при первом запуске или по кнопке.

- **Поле лимита тока в приложении (v1.9)** показывается только после ответа прошивки на `{7}` - так старые прошивки не получают неизвестные команды.
  `{7}` добавлен в список запросов, которые прошивка выполняет заново при повторе с тем же seq (иначе потерянный ответ не восстановить).

- **Хост-тесты собирают настоящие `.ino` с заглушками, без выноса логики и без PlatformIO `native`/Unity.** Причина: так проверяется ровно тот код,
  что идёт в прошивку, нет дублирования, правка прошивки минимальна (вынесены только структуры EEPROM в `types.h`), а тесты запускаются одной командой
  `make -C tests` даже в песочнице без доступа к реестрам PlatformIO. Сборка с AddressSanitizer + UBSan ловит выходы за границы и деление на ноль.
  Проверено мутациями: удаление защиты от деления на ноль, от индекса калибровки, дедупликации ACK и коэффициента 0.7 приводит к падению тестов;
  удаление защиты от отсутствия избранных эффектов приводит к зависанию (CI-задание с `timeout-minutes: 5`).

- **FastLED берётся из реестра PlatformIO и закреплён на 3.5.0**; вендорная копия 3.4.0 (1,8 МБ, большая часть кода репозитория) удалена. 3.9.0 не собирается:
  прошивка вызывает `strip->showLeds()` и `clearLedData()` напрямую, в новых версиях они недоступны. Обновление дальше требует переписать вывод на `FastLED.show()` -
  отдельная задача. EEManager (адрес `uint16_t`) и SimplePortal (форма пароля точки) изменены в проекте, EncButton 1.x несовместим с актуальными версиями - они остаются в `libraries/`.
- **Стенд протокола** (`tests/protocol_stand.py`): Python-клиент (порт `ack.pde`) против настоящего кода прошивки, собранного как UDP-сервер, через прокси с потерями 30%.
  Проверено мутацией: без дедупликации ACK команда «следующий эффект» выполняется 7-11 раз вместо 6.
- **APK уходит в Releases через одноразовый workflow** `release-apk.yml` (у сессии нет инструмента создания релизов; workflow создаёт релиз из APK в репозитории).
  Порядок: слить PR с workflow → запустить → проверить релиз → отдельным PR удалить APK и workflow.

- **APK удалён из дерева репозитория** (релиз `app-v1.7` создан одноразовым workflow, сам workflow удалён). Бинарник остаётся в истории git, поэтому размер
  репозитория не уменьшился. Новые версии приложения собираются вручную (Processing/Android Studio) и прикладываются к релизу в GitHub; приложение из исходников v1.9
  в релиз пока не выложено.

## 2026-10-20
- **Веб-интерфейс: встроенный `ESP8266WebServer` + JSON API + опрос раз в 2 с**, а не ESPAsyncWebServer + WebSocket из первоначального плана. Причины: ни одной внешней библиотеки
  (меньше рисков сборки на ядрах 2.7.x и 3.x), обработчики запускаются на ПК через заглушку класса и тестируются как есть, живые обновления для гирлянды не критичны.
- **Страница вшита в прошивку (gzip, PROGMEM), а не лежит в LittleFS**: не нужна отдельная загрузка файловой системы, одна прошивка = всё. Готовый `web_page.h` лежит в
  репозитории (для Arduino IDE и сборки без Python), `tools/gen_web.py --check` в CI следит за актуальностью (сравнивается распакованное содержимое, не байты gzip).
- **CSRF-защита заголовком `X-Requested-With`** на всех POST: без пароля это единственное, что мешает произвольному сайту в браузере управлять гирляндой в локальной сети.
- **Одна логика настроек для UDP и веба** (`settings.ino`): `parsing.ino` вызывает те же функции; тест сравнивает результат обоих способов.
- Хост-сервер для e2e-тестов: заглушка `ESP8266WebServer` умеет и вызов обработчиков без сети (`test()`), и настоящие HTTP-запросы; страницу проверяет Playwright в Chromium.

- **Сцены: один файл `/scenes.bin` фиксированного размера (8 мест) в LittleFS**, а не отдельный файл на сцену и не EEPROM: EEPROM заполнен блоками калибровки и его раскладку нельзя менять,
  фиксированный размер упрощает проверку, 712 байт в ОЗУ - пренебрежимо. Защита: версия + Fletcher-16 + проверка значений при чтении; запись через временный файл и переименование.
  В сцену не входят питание, число светодиодов и лимит тока - они описывают установку, а не вид.

- **Редактор координат: hex в JSON/теле запроса и подсветка через `calibF`.** Координаты 500 светодиодов - 2000 hex-символов: проще и надёжнее бинарного обмена (нет проблем с нулевыми байтами в `String`),
  читается и в логах. Запись «всё или ничего» с защитой `n` от гонки при смене числа светодиодов. Подсветка светодиода использует тот же флаг `calibF`, что и калибровка по UDP,
  и гаснет сама через минуту (`hlTmr`), если страница закрылась. Общий расчёт границ вынесен в `recalcBounds()` и используется и UDP-калибровкой, и редактором.
- **Страница: чистые функции (геометрия карты, имена) проверяются `node --test web/test`** - они не зависят от DOM и импортируются тестом напрямую.

- **Калибровка по видео: маркер + расписание вместо синхронизации по часам.** Часы телефона и ESP не связаны, поэтому момент старта берётся из самого видео: перед серией горит маркер (до 25 светодиодов, чтобы ток был мал),
  страница находит его по парным фронтам яркости, дальше слоты светодиодов известны по расписанию. Светодиод ищется по разности «слот i против слота i-1» (ловит только появившееся пятно).
  Проверено синтетическими кадрами (шум, лампа, движущееся пятно, дрейф экспозиции, светодиоды вне кадра, чёрные первые кадры, сдвиг часов 40 мс, 500 светодиодов) и настоящим видео VP8, сделанным ffmpeg, в Chromium.
- **Устаревшие кадры при перемотке видео** (`drawImage` сразу после `seeked` рисует прежний кадр) терялись у отдельных светодиодов (peak = 0 при разных запусках): теперь ждём `requestVideoFrameCallback`, а побитово совпавший с предыдущим кадр
  при другом времени снимается заново. Ошибка была видна только в настоящем браузере и недетерминированно - поэтому e2e гоняет настоящее видео, а не только синтетические кадры.
- **Первые 0,2 с видео не участвуют в поиске маркера**: ещё не декодированный кадр даёт ложный «скачок яркости» (найденный баг).

- **OTA только в окне, которое открывает физическое действие (три нажатия кнопки, 5 минут).** Пароль не подходит: у гирлянды нет дисплея и нет защищённого канала для его ввода, а постоянно открытый
  `/update` позволил бы любому в сети WiFi прошить устройство. Окно закрывается по времени и после успеха; кроме окна нужен заголовок страницы (CSRF), образ проверяет `Update` (байт 0xE9, размер).
  Свой обработчик загрузки вместо `ESP8266HTTPUpdateServer`: библиотечный не даёт проверить окно и заголовок до начала записи.
- **Размер прошивки ограничен в CI (900 КБ)**: OTA требует, чтобы образ помещался в раздел обновления (около 1 МБ на d1_mini).
- **`bool otaBusy` объявлена в главном файле**, а не в `ota.ino`: переменные, нужные в `loop()`, должны быть объявлены до него (вкладки склеиваются после главного файла; для функций Arduino делает прототипы, для переменных - нет).
